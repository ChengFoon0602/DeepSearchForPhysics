### 2.3 两个"README 没告诉你"的硬事实

1. **启动命令是错的**：README 写 `python api/server.py`。实际跑会 `ModuleNotFoundError: No module named 'agent'`。
   - 原因：`python 脚本路径` 时 `sys.path[0]` 指向脚本所在目录（`api/`），项目根目录不在 path 上。
   - 正确：`python -m api.server`（`-m` 以当前目录为基准）。
   - 排查手段：5 秒实证——建一个 `api/server.py` 里 `import agent` 的最小复现，两种启动方式各跑一次，肉眼确认。

2. **"数据库/RAGFlow 可选"只指配置可选，不是依赖包可选**：`main_agent.py` import 时就硬加载 `mysql.connector`、`ragflow_sdk`、`tavily`、`langchain-openai`。所以包必须全装，`.env` 的 key 才可以不填。

## 三、踩坑实录：12 个问题的排查与 Debug

> 每个问题都按「现象 → 排查 → 根因 → 解决 → 方法论」五段写。方法论那行是能迁移的。

### 问题 1：主智能体"就绪待命"，不干活

- **现象**：发"搜索一下最近 AI Agent 领域的最新进展"，模型回"工作目录已就绪，当前为空目录，等待任务"，没调用任何工具，也没生成文件。
- **排查**：看服务器日志——`session_created` 有、`loop: True` 有，但**没有任何 `assistant_call` / `tool_start`**。
- **根因**：`run_deep_agent` 把一段【工作环境指令】追加到**每次** query 后面，内容写得像系统提示词（"系统会提供工作目录…规则 1-4"）。模型把整条消息误读成"初始化握手"，于是自我介绍、等待任务。
- **解决**：换更明确、带产出物的 query（也建议走 Swagger，避免 PowerShell 中文编码干扰）。
- **方法论**：**用"有没有调用工具"来区分「链路问题」还是「模型行为问题」**。链路问题看事件流是否完整；模型行为问题看它到底听懂了什么。别急着改代码，先判断是哪一类。

### 问题 2：生成的 Markdown 里公式渲染不出来

- **现象**：md 文件里 `\(T = 2\pi\sqrt{I/(mgd)}\)` 以原文显示。
- **排查**：**打开生成的文件看真实内容**（而不是猜）——LaTeX 语法完全正确，问题出在**分隔符**。
- **根因**：模型输出的是 LaTeX 原生分隔符 `\(...\)` / `\[...\]`，但 Markdown 生态的渲染器（Typora、VS Code 预览）只认 MathJax 风格的 `$...$` / `$$...$$`。
- **解决**：prompts.yml 加规则"行内公式用 `$...$`，独立公式用 `$$...$$`，严禁 `\(...\)`"。网页端则引入 KaTeX + marked 渲染。
- **方法论**：**区分"语法"和"分隔符"两个层面**。语法错是模型没写对；分隔符错是格式约定不匹配。看产物、看渲染器的约定，别先怀疑 LaTeX 本身。

### 问题 3：没要求，却自动生成并转 PDF

- **现象**：query 只让验证公式，agent 却生成 MD + 转 PDF。
- **排查**：读 main_agent 的 system_prompt——"文件生成"规则写得非常重（"你可以生成 Markdown、PDF"），而"没明确要求就文本回复"只出现一次、无约束力。
- **根因**：**prompt 的权重分配决定了模型的默认行为**。规则多、语气强的一方赢。
- **解决**：在【关键执行顺序】加硬规则（"严禁自动转 PDF"），并让"默认生成 MD"成为条件触发（涉及公式/综述才生成，简单问答直接回复）。
- **方法论**：模型默认行为 = 提示词里哪条规则**说得最重**。要改变默认行为，用【关键执行顺序】/"严禁"这类强约束，别指望一条轻描淡写的规则。

### 问题 4：加了规则，模型还是随机站队（本次最核心）

- **现象**：改完默认生成 MD 的规则后，重发复摆 query，**又不生成文件了**。
- **排查**：读 prompts.yml **全文**——不是只看自己改的部分。发现第 27 行：*"你**没有生成文件的能力**，只能交给文件生成助手去解决"*。但：团队里根本没有"文件生成助手"；第 30 行又说"你掌握的工具包括 generate_markdown"。
- **根因**：**同一个 prompt 内自相矛盾**（一句说"你不能生成"，一句说"你有生成工具"）。模型面对矛盾规则是**随机站队**的——所以它第一次生成、第二次不生成，行为不稳。
- **解决**：删掉"你没有生成文件的能力"，统一为"所有文档由你自己生成"。顺带修了另外两处引用不存在的"文件生成助手"的地方，团队数量改成"多个"。
- **方法论**：**prompt 自相矛盾 → 模型随机站队，这是行为不稳的第一嫌疑**。修行为问题，先通读整个 prompt 找自洽性，别在矛盾之上叠新规则。

### 问题 5：DeepSeek 网络瞬断（上游故障）

- **现象**：服务器控制台 `[Monitor:error] 执行主智能发生异常信息：('Connection aborted.', RemoteDisconnected('Remote end closed connection without response'))`。
- **排查**：`RemoteDisconnected` 是"连接被对端关闭、无响应"，是**网络层**错误，不是 401/404（那是鉴权/模型问题）。重试一次即好 → 确认是瞬断。
- **根因**：DeepSeek 服务端抖动 / 网络瞬断 / 长连接复用被服务端关闭。
- **解决**：重试。若频繁，给 `llm.py` 的 `init_chat_model` 加 `max_retries=3, timeout=60`（只重试 HTTP 请求本身，幂等安全）。
- **方法论**：**先区分上游错误和代码 bug**。网络层错误（RemoteDisconnected/Timeout）先重试；如果重试就好，别改代码。要区分：401/403=鉴权，404=配置错，RemoteDisconnected=网络。

### 问题 6：下载列表混入上次的报告

- **现象**：前端下载栏同时显示这次和上次生成的报告。
- **排查**：看 `main_agent.py` —— `session_dir = output/session_{thread_id}`，**按 thread_id 建目录**；前端把同一个 thread_id 存在 localStorage 反复复用 → 同一目录累积所有历史文件。
- **根因**：**会话目录是"工作区"语义（一个线程一个目录），不是"单次任务"语义**。`/api/files` 列目录里所有文件。
- **解决**：前端记录 `taskStart`，`loadFiles` 只显示 `mtime >= taskStart` 的文件。展示层过滤，服务端不动。
- **方法论**：**先理解设计语义再决定在哪层修**。这里是"工作区"语义，行为合理，只是展示层需求——所以改前端过滤，而不是改后端目录结构。

### 问题 7：静态挂载后 API 的 405 变成了 404

- **现象**：加了 `app.mount("/", StaticFiles(...))` 后，`GET /api/task` 从预期的 405 变成 404。
- **排查**：用"错误方法"访问 API 路径做测试，暴露了路由优先级问题。
- **根因**：Starlette 匹配路由时，路径对但方法不对 → `Match.PARTIAL`，路由器**继续往后找 full match** → 被 `"/"` 兜底挂载接住 → 当静态文件返回 404。
- **解决**：不需要修——真实调用（方法正确）路径先 full match，轮不到挂载。只是"用错方法"的边角从 405 变 404。
- **方法论**：**用"错误方法"测试会暴露路由匹配细节**。挂载 `/` 兜底是常见做法，但要理解它和 partial match 的交互。

### 问题 8：SqliteSaver 三连坑（本次最硬）

- **现象与排查**，一步一步来：

| 尝试 | 报错 | 说明 |
|------|------|------|
| ① 同步 `SqliteSaver` + `check_same_thread=False` | `The SqliteSaver does not support async methods. Consider using AsyncSqliteSaver` | 图用 `astream()` 异步执行，同步 saver 不支持异步方法 |
| ② `AsyncSqliteSaver` 在模块级建 | `RuntimeError: no running event loop` | `AsyncSqliteSaver.__init__` 里调用 `asyncio.get_running_loop()`——**必须在运行中的事件循环里构造** |
| ③ `asyncio.run(aiosqlite.connect(...))` | `ValueError: a coroutine was expected` | `aiosqlite.connect()` 返回可 await 的 Connection，不是 coroutine，`asyncio.run` 不吃；包一层 `await` 才连上 |
| ④ 建好后 CLI 跑完不退 | 进程挂住 | aiosqlite 连接的后台线程是**非守护线程**，主线程结束要等它（服务器不受影响） |

- **根因**：AsyncSqliteSaver 的设计约束是"必须活在事件循环里"。这和项目"模块级构建图"的结构冲突。
- **解决**：把图的构建从模块级改成**懒加载**——`get_main_agent()` 在第一次跑任务时（已在 uvicorn 事件循环内）建连接、建图，加锁防并发双建。
- **验证**：真实 uvicorn 服务器上跑通——报告生成 + `checkpoints` 表 40 行落盘 + 重启后记忆还在。
- **方法论**：**框架报错要认真读，报错本身就是答案**。这个报错直接告诉你该用哪个类、约束是什么。看 API 用 `inspect.signature()` 确认，别猜。**架构约束（要 running loop）不是 bug，是设计——它逼你把"模块级构建"改成"循环内懒加载"，这是正确方向。**

### 问题 9：前端"记录"按钮点击没反应（异步状态卡死）

- **现象**：发送按钮点击无任何反应，Enter 也不触发。
- **排查**：先读代码确认接线在（`sendBtn.onclick = send` 存在、脚本没有中途抛出）→ 再追状态流转——发现 `busy` 只有 `task_result` / `error` 两个事件能重置，但页面**没有 `onclose` 处理、没有超时兜底**。
- **根因**：`send()` 里 `busy = true; 按钮 disabled` 之后，若 WebSocket 中途断开（调试时重启过服务器 / 网络抖动），两个终态事件都不会来 → `busy` 永远为 `true` → 按钮永远 disabled。**连接断开是静默的，页面根本不知道**。
- **解决**：四个兜底——① `ws.onclose` 里 `if(busy) finish()` 并提示"连接已断开"；② `ws.onerror` 同样重置；③ 5 分钟看门狗 `setTimeout`（`finish()` 时清除）；④「新会话」也重置 busy。
- **方法论**：**异步状态必须有"终态恢复路径"**（onclose / onerror / 超时看门狗），否则状态会静默卡死。设计任何前端异步流程，问自己三个问题：正常完成怎么办？报错怎么办？**断连 / 无响应怎么办**？——最后那个是永远要补的兜底。

### 问题 10：前端"发送"按钮没反应——两个独立问题叠加

> 注：问题 9 的 busy 恢复路径是值得保留的健壮性改进（防御性），但并非本次"没反应"的直接原因。Playwright 排查 + 用户澄清后，真相是两件事叠加。

- **现象**：点「记录」按钮没反应。
- **排查**：
  - **用户澄清（实际遇到）**：按钮文案「记录」误导，以为是"记录"按钮；且**输入框是空的**。`send()` 开头 `if (!q || busy) return`——**空输入直接静默返回**，什么都不发生。
  - **Playwright 独立发现（真实问题）**：`file://` 加载页面 → 脚本执行、点击后用户消息出现 → 前端代码正常；全新 8013 实例 → 点击 → `POST 200` → 链路正常；访问 8000 → 浏览器请求挂起 → **8000 实例坏**。
- **根因**：① 空输入 + 误导性文案（用户实际体验）；② SqliteSaver 调试期留下的坏服务器实例（独立、真实）。
- **解决**：① 按钮文案「记录」→「发送」；② 干净重启服务器（叉掉窗口 → 确认端口释放 → `python -m api.server`）。
- **方法论**：**"没反应"先查输入是否为空、按钮语义是否清晰**——`if (!q) return` 守卫对空输入是静默的，配上误导文案就是"点了没反应"。**再分清客户端 vs 服务器侧**：纯客户端按钮（#new）能用、触发请求的按钮（#send）不能用 → 问题划到服务端。**验证前端用 `file://` 绕过服务器；对比"全新实例 vs 当前实例"定位代码还是环境。**

### 问题 11：agent 记不住之前的会话——记忆是线程级的

- **现象**：新开一个会话问 agent"之前做到哪了"，它回"工作目录为空，找不到任何记录"。
- **排查**：它检查的是 `output/session_{新thread_id}`——新线程刚建的空目录；检查点表里确实没有这个线程的历史。
- **根因**：**agent 的记忆是"线程级"的**：只有当前 `thread_id` 的检查点 + 当前工作目录。新线程 = 全新上下文 + 空目录。跨线程隔离是刻意的安全设计（防止 agent 乱翻别的会话的文件）。
- **解决**：同一线程内继续（不点「新会话」，SqliteSaver 保证跨重启不丢）；跨线程续接需要额外功能（给 agent 加"查看历史输出"工具，会削弱隔离，不建议）。
- **方法论**：**理解系统的"记忆边界"**——它记住什么、不记住什么，是设计决策不是 bug。诊断"为什么记不住"，先确认边界在哪一层（线程级 / 会话级 / 全局级）。

### 问题 12：新会话找不到项目上下文——缺 CLAUDE.md

- **现象**：项目目录里新开一个 Claude 会话，它不知道项目是什么、怎么启动。
- **排查**：项目根目录没有 CLAUDE.md；`output/` 里十几个 session 目录混着空目录和带文件的，新会话无法从磁盘推断项目脉络。
- **根因**：**"约束先行"原则没落实**——搭了整个项目却没写项目说明书。
- **解决**：补一个项目 CLAUDE.md（项目是什么、启动命令、文件地图、已知坑、学习日记位置）。
- **方法论**：**可复用项目的第一个交付物不是代码，是 CLAUDE.md**。它让任何未来的会话（包括几个月后的自己）一进目录就能接上，不靠对话记忆。

## 四、Debug 方法论总结（可迁移）

1. **先定位问题层级**：是「链路问题」（事件流不完整）还是「模型行为问题」（模型没按预期做事）？链路问题看日志事件，模型问题看 prompt 和产物。
2. **看真实产物，不要只看日志**：公式渲染问题，打开生成的 md 文件看内容；文件生成问题，看 output 目录里到底有没有文件。
3. **读完整 prompt，别只读自己改的部分**：模型行为不稳，第一嫌疑是 prompt 自相矛盾（模型对矛盾规则随机站队）。
4. **框架报错 = 答案**：认真读报错原文，它通常直接告诉你该用什么类、什么约束。用 `inspect.signature()` 确认 API。
5. **5 秒实证 > 猜**：sys.path 行为、路由优先级这类，写个最小复现跑一下，结论靠实验不靠记忆。
6. **区分上游错误和代码 bug**：网络层错误先重试；重试就好 = 瞬断，别改代码。
7. **测试要覆盖"错误用法"**：用错误方法访问 API 会暴露路由优先级，用 TestClient 能暴露 TestClient 独有的问题（记得和真实服务器对照）。
8. **一个原因一个原因排除**：SqliteSaver 的报错链是逐步收窄的——每修一个，报错就前进到下一个更具体的约束。
9. **异步状态必须设计终态恢复路径**：onclose / onerror / 超时看门狗。前端异步流程问自己三个问题——正常完成怎么办？报错怎么办？**断连 / 无响应怎么办**？最后一个是永远要补的兜底。
10. **前端"没反应"先分客户端 vs 服务器侧**：纯客户端按钮能用、触发请求的按钮不能用 → 问题在服务端。验证前端用 `file://` 绕过服务器，对比"全新实例 vs 当前实例"定位代码还是环境。
11. **理解系统的"记忆边界"**：记住什么、不记住什么，是设计决策。诊断"记不住"，先确认边界在哪一层（线程级 / 会话级 / 全局级）。
12. **新项目先写 CLAUDE.md**：可复用项目的第一个交付物，让任何未来会话一进目录就接上。

## 五、知识点沉淀

- **多智能体编排（orchestrator）**：主智能体不自己干活，按需求调度子智能体。deepagents 只需 name/description/system_prompt/tools 四个字段。
- **优雅降级**：README 说的"可选"——配置不填，主智能体靠 prompt 判断跳过。前提是 prompt 要诚实（不存在的服务别写进团队名单）。
- **ContextVar vs 全局变量**：FastAPI 多请求跑在同一个线程的不同协程里，全局变量会串台；ContextVar 是协程级隔离。
- **WebSocket 推送的时序**：先建连接再发任务，否则前几个事件会丢（服务端按 thread_id 查连接池）。
- **checkpointer 的三个 saver**：
  - `InMemorySaver`：内存态，重启丢；
  - `SqliteSaver`：同步，`astream` 用不了（不支持 async 方法）；
  - `AsyncSqliteSaver`：异步，**必须在事件循环里构造**。
- **checkpointer 不只存历史**：它还决定图能否从中间节点续跑——这是后面"人工审批节点"（human-in-the-loop）的基础。
- **aiosqlite 的线程模型**：连接跑在独立线程的事件循环里，不绑定调用方 loop；非守护线程会让 CLI 脚本退出时挂住。

## 七、本地 RAG 知识库：把 RAGFlow 换成真能跑的管线

> 2026-08-12 · 把项目里唯一"注册但不能用"的 RAGFlow 子智能体，换成本地 Chroma + fastembed 的完整 RAG 管线。无 Docker、无守护进程，全 pip 包。

### 7.1 为什么换

四个子智能体里只有 RAGFlow 是不可用的——要部署服务端（Docker）。而 RAG 恰恰是求职最热门的能力。方案：**本地部署 = 不部署任何服务端**，用纯 pip 包搭一条完整可演示、能讲清每个设计决策的管线：

```
文档 → 切分(chunking) → 嵌入(embedding) → 向量库存储 → 检索(top-k) → 组装上下文喂给主智能体
```

选型：**Chroma**（嵌入式向量库，API 与 Pinecone/Qdrant 一致，简历最像生产）+ **fastembed**（ONNX，不需要 PyTorch）+ **BAAI/bge-small-zh-v1.5**（中文，dim 512，~90MB，离线可用）。切分复用已有的 `langchain_text_splitters`，PDF 复用 `pypdf`，新增依赖只有 2 个包。

### 7.2 关键文件

| 文件 | 作用 |
|------|------|
| `kb/docs/` | 源文档目录（人维护）：复摆笔记 + 学习日记，做两个 demo 场景 |
| `ingest_kb.py` | 入库脚本：切分(500/80) → 嵌入 → 写 Chroma；**重跑=清空重建**（幂等） |

| `prompt/prompts.yml` | `ragflow:` key → `kb:`，重写 description/system_prompt |

### 7.3 踩坑实录

#### 问题 13：langchain `@tool` 装饰的不是普通函数

- **现象**：自检脚本 `search_knowledge_base("复摆周期公式", top_k=3)` 直接 `TypeError: 'StructuredTool' object is not callable`。
- **排查**：报错本身就是答案——`@tool` 返回的是 `StructuredTool` 实例，不是函数。
- **解决**：用 `.invoke({'query':..., 'top_k':...})`（或 `.func(...)`）调用。
- **方法论**：**framework 包装后的对象先看类型**。别假设装饰器返回的还是原来的签名，`type()` / `dir()` 看一眼再写调用代码。

#### 问题 14：`from agent.main_agent import main_agent` 导入失败

- **现象**：按学习日记 2.1 写的自检命令跑不了——`ImportError: cannot import name 'main_agent'`。
- **根因**：模块导出的是 `_main_agent`（懒加载全局）+ `get_main_agent()` 工厂，**没有** `main_agent` 这个名字。自检命令写错了。
- **解决**：自检用 `import agent.main_agent`（能 import 就说明链路通），或 `from agent.main_agent import get_main_agent`。
- **方法论**：**文档里的命令也会过期**。重跑旧命令报错时，先读源码看导出名，别硬猜。

#### 问题 15：YAML key 改名必须和代码 import 原子落地

- **现象**：`knowledge_base_agent.py` 改成 `sub_agents_content['kb']` 后，prompts.yml 还没改前 import 直接 KeyError。
- **根因**：两个文件强耦合——代码要的 key 和 YAML 里的 key 必须同时改。
- **解决**：一次性把 `prompts.yml` 的 `ragflow:`→`kb:` 和 `knowledge_base_agent.py` 一起改完，再重启。
- **方法论**：**配置与消费它的代码是一组变更，不是两件事**。改配置必搜所有消费方（grep key 名），确认全链路一致再动。
